## What This Is

A public website at **joemirza.com** that displays economic and financial data with
interactive charts and tables. Built 2026-03-05; now four live tabs plus a shared
recession-shading dataset.

## Architecture

```
scripts/           Python data fetchers (one per series)
data/              Raw JSON output from fetchers (committed to repo)
site/              Static site served by GitHub Pages
  index.html       Single-page app with Plotly.js charts
  data/            Copy of JSON data (deployed to gh-pages branch)
.github/workflows/ GitHub Actions for daily data refresh + deploy
```

- **No server / no backend** — entirely static, hosted free on GitHub Pages
- **Data flow**: Python script → `data/<name>.json` (committed to `main` by hand/PR) →
  workflow copies `data/` → `site/data/` → deploys `site/` to the `gh-pages` branch via
  `peaceiris/actions-gh-pages`. **The workflow never commits fetched data back to
  `main`** — `main`'s `data/*.json` only updates when someone commits it, so it can
  lag what's actually live on `gh-pages`/joemirza.com. Don't assume `data/*.json` on
  `main` reflects current published data without checking.
- **Frontend**: Vanilla HTML/CSS/JS with Plotly.js for interactive charts
- **Custom domain**: CNAME file in deploy sets `joemirza.com`; DNS A records point to
  GitHub Pages IPs (configured in Porkbun)

## Local Iteration Loop

`scripts/dev.sh [port]` (default 8888): copies `data/*.json` → `site/data/`, prints
a staleness warning per series, then serves `site/` with `python3 -m http.server`.
No network calls, works with `FRED_API_KEY` unset — it only reads what's already
committed to `data/`.

The staleness warning matters because local `data/*.json` is known to lag production
(see Architecture above — the workflow never commits fetched data back to `main`).
`dev.sh` surfaces this instead of silently serving old data as if it were current;
it warns, it doesn't block, since UI iteration usually doesn't need fresh data.

**The loop**: edit `site/index.html` (or a fetch script + rerun it locally with
`FRED_API_KEY` set) → `scripts/dev.sh` → reload `http://localhost:8888` → check the
result with a Claude in Chrome screenshot → commit and push. The daily workflow
handles fetching and deploying; this loop is only for checking a change works before
it ships.

## Correctness Tests

`tests/` (pytest) checks the data fetchers against independent sources and internal
invariants: `test_data_integrity.py` (dates unique/monotone, no FRED `"."` sentinel
became 0, P/E internal arithmetic, the known header/earnings mismatch below — no
network needed), `test_fred_utils.py` (unit tests on the shared FRED helper, mocked,
no network), `test_spreads.py` / `test_yield_curve.py` / `test_sp500_pe.py` (sampled
dates cross-checked against FRED's own `T10Y2Y`/`T10Y3M`, a direct `DGS*` pull, and
Shiller's own P/E columns — need network + `FRED_API_KEY`), and `test_staleness.py`
(each series' last observation within its expected publication lag).

Run locally: `pip install -r requirements-test.txt && FRED_API_KEY=xxxxxxxxxxxxxx pytest`.
Tests needing network are marked `network` and skip automatically without a working
connection; run `pytest -m "not network"` to skip them deliberately.

**Staleness source matters**: `test_staleness.py` checks the *live* site
(`https://joemirza.com/data/*.json`) by default, because local `data/*.json` is known
to lag (see Architecture above) — checking it locally would just re-report that known
gap every time. Set `STALENESS_SOURCE=local` to check the local `data/` copy instead;
the CI workflow does this, running the check right after that day's fetch and before
deploy, when local `data/` is the freshest copy that exists.

**Known failing check, not yet fixed**: `test_sp500_pe_header_matches_latest_observation_earnings`
is `xfail`. `sp500_pe.json`'s header `last_ttm_earnings` (222.53 as of 2026-09-12)
disagrees with the earnings every recent observation actually uses (234.06) —
`get_ttm_for_month()` in `fetch_sp500_pe.py` always marks the newest earnings-overrides
entry as `estimated: True`, so the header's "last confirmed" figure is one quarter
behind what the chart plots. Fixing it is a code/data change, not a test change; remove
the `xfail` mark once `fetch_sp500_pe.py` is fixed.

## S&P 500 P/E — Quarterly Earnings Update (4x/year)

The `data/earnings_overrides.json` file must be manually updated each earnings season
(roughly Feb, May, Aug, Nov) when S&P Global publishes the latest quarterly scorecard.

**Steps:**
1. Download the new `sp-500-eps-est.xlsx` from S&P Global and replace `reference_resources/sp-500-eps-est.xlsx`
2. Run `python3 scripts/build_earnings_overrides.py` to regenerate `data/earnings_overrides.json`
3. Commit and push — the next GitHub Actions run will pick up the new earnings.

**Known gap (as of 2026-09-12):** `reference_resources/sp-500-eps-est.xlsx` was last
refreshed 2026-03-08 (quarter ending 2025-09-30). The live P/E series has been running
on `estimated: true` earnings since — every observation from Oct 2025 onward reuses
that same 234.06 TTM figure. Needs a fresh xlsx download from S&P Global before the
next EPS update step is run.

## Development Patterns

When adding a new data series:
1. Create a new Python script in `scripts/` (follow `fetch_treasury.py` pattern)
2. Output JSON to `data/<series>.json`
3. Add the fetch command to `.github/workflows/update-data.yml`
4. Add a new tab and chart/table section in `site/index.html`
5. Add a `cp data/<series>.json site/data/` line in the workflow

The architecture was chosen specifically to scale this way without rework.

## Tech Choices & Rationale

- **Plotly.js** (not matplotlib): Interactive browser charts, supports dropdowns/tabs natively
- **Static site** (not Streamlit): Full control over UI, free hosting, custom domain support,
  no server to maintain
- **GitHub Actions** (not a cron server): Free, reliable, no infrastructure to manage
- **Vanilla JS** (no React/framework): Keeps it simple for now; can migrate later if needed
- **No database**: JSON files are sufficient for this scale; easy to add SQLite or similar later

## Chart Conventions

**Established:**
- Recession shading (USREC) on every time-series chart.
- Monthly-era points labelled as such in the tooltip ("Monthly observation, source: X");
  never upsample monthly to daily.
- Make data gaps (e.g. the yield curve's 2002–2006 tenor gap) visible; don't interpolate
  across them.
- Sequential colour scale for heatmaps; diverging (red/blue) for spreads where zero is meaningful.
- Label the current curve with actual values on the snapshot chart.
- Categorical (evenly spaced) tenor axis on curve snapshots — Bloomberg convention.
- FRED's `"."` is missing, never zero.

**Adopted 2026-09-12:**
- No dual y-axes — **held lightly**, not a hard rule. Dual axes have real uses (two
  series each readable in their own units, easy lead/lag comparison) and no chart
  built so far needs one. Show relationships instead as a scatter plot, a derived
  series, or stacked panels sharing the time axis. Revisit if a future chart
  genuinely wants two axes rather than writing an exception clause preemptively.
- Every chart image carries a short source line and the date of its latest real data
  (not the pipeline run time), drawn inside the Plotly chart itself so PNG exports
  and cropped screenshots keep it (the HTML subtitle does not survive the camera
  button). Full detail goes in the chart's About tab.
- Series that compound over decades plot on a log axis, labelled as log. Doesn't
  apply to yields, ratios, or spreads — only to price levels held over long spans.

Full rationale for the 2026-09-12 additions is in the Session Plan decisions table at
`~/Obsidian/Investing/Finance and Economic Data Website/Session Plan.md`.

## Licence Notes

- **FRED** (St. Louis Fed) series used here (DGS10, DGS2, DGS3MO, DGS1MO–DGS30, USREC)
  are public domain. FRED also carries provider-copyrighted series (e.g. ICE BofA
  `BAML*` OAS, S&P DJI Case-Shiller) with their own republication terms — read the
  series notes on FRED before adding one of those.
- **Shiller/Yale** `ie_data.xls` (used by `fetch_sp500_pe.py` for pre-1953 history) is
  a free public download; no republication restriction found.
- **S&P Global** `sp-500-eps-est.xlsx` (quarterly EPS, `data/earnings_overrides.json`)
  is used as a manually-downloaded input; no explicit redistribution terms have been
  verified. We publish only the derived TTM EPS figure, not the source file.

# Then open http://localhost:8888 — see Local Iteration Loop above
