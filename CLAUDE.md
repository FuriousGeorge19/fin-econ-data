# fin-econ-data — Project Context for Claude

## What This Is

A public website at **joemirza.com** that displays economic and financial data with
interactive charts and tables. Built 2026-03-05 as a single-file dashboard; rebuilt
2026-09-13–14 (`s5-chart-components`) into a generated multi-page site — one page per
chart, three section pages, a shared recession-shading dataset, and a component system
(chart-type modules + per-series config) for adding more without editing shared files.

**Cross-session plan lives outside this repo**: `~/Obsidian/Investing/Finance and
Economic Data Website/` holds the user's goals (`What I Want.md`), the multi-session
build-out plan (`Session Plan.md`), and the latest `HANDOFF — <date>.md` snapshot.
Read the handoff first at the start of a planning session — this repo's CLAUDE.md and
ARCHITECTURE.md describe the build, not the roadmap or its rationale.

## Architecture

```
scripts/
  fetch_<name>.py       one Python fetcher per data source (stdlib only, except
                         fetch_sp500_pe.py which also needs pandas/xlrd/openpyxl)
  fetch_all.py          runs every series' fetcher, catches per-series failures,
                         writes data/fetch_status.json — replaces per-series
                         workflow steps
  build_site.py         the site generator (stdlib only) — reads series/*.json +
                         pages/*.json, writes the multi-page site under site/
  series_meta.py, staleness.py, build_earnings_overrides.py   shared helpers
  catalog.py            the source catalogue's loader/validator/resolver/report
                         (`check [path…]`, `report [--topic T]`); series_meta.py
                         calls it at fetch time to resolve a descriptor's sources
series/<id>.json        hand-maintained descriptor per dataset: meta fields (title,
                         units, cadence, methodology, notes), `sources` as
                         references into catalog/ (`{slug, dataset?, url?, note?}`
                         — name and licence come from the catalogue), PLUS an
                         optional "presentation" block (which section(s) it's on,
                         order, chart type + options, stats, table). No
                         "presentation" = a data-only dataset with no page (usrec).
catalog/sources/<slug>.json  the source inventory: one file per rights holder —
                         access, terms (with status + verbatim quote), datasets
                         (cadence, coverage, lag, topics, `via` for data hosted
                         on FRED). catalog/README.md holds the rules and field
                         table; catalog/research-log.md the productive searches
pages/site.json         site name + the three sections (id, label, tagline)
pages/<slug>.json       curated page manifests; home.json → /
data/<id>.json          raw fetcher output — committed, but test fixtures on
                         `main`, not the deploy history (see below)
site/css/, site/js/     COMMITTED sources: site.css (+ tokens.css for colour
                         values), app.js (page entry point), js/lib/ (shared
                         runtime: card.js, plotly-layout.js, presets.js, dates.js,
                         theme.js, data.js, export.js, asof.js), js/charts/
                         (chart-type modules: timeseries.js, curve.js, sp500_pe.js)
site/*.html, site/data/ GENERATED by build_site.py — gitignored; rebuilt by
                         scripts/dev.sh locally and by the workflow before deploy
.github/workflows/      GitHub Actions: daily fetch + generate + deploy
```

- **No server / no backend** — entirely static, hosted free on GitHub Pages
- **Data flow**: the workflow seeds each `data/<id>.json` from the live `gh-pages` copy
  first (`git fetch --depth=1 origin gh-pages` + a per-file `git checkout FETCH_HEAD --`,
  named files only — never the directory, since `data/earnings_overrides.json` is a
  fetch-time input, not a published series, and a directory-level restore would delete
  it), then `scripts/fetch_all.py` runs every fetcher (each descriptor's `fetcher` key,
  default `fetch_<id>.py`), catching failures per series into `data/fetch_status.json`
  rather than failing the step — so one series' fetch failing leaves that series on
  yesterday's live data (seeded above) while the others still update; the deploy
  always runs. A final step exits 1 (after the deploy) if any fetch failed, so the job
  goes red and GitHub notifies without blocking the site update. The workflow **never
  commits fetched data back to `main`** — `main`'s `data/*.json` are test fixtures, not
  the deploy history; `gh-pages` is. Don't assume `data/*.json` on `main` reflects
  current published data without checking; `scripts/dev.sh --live` pulls the live copies
  down for local work that needs them.
- **Site generation**: `scripts/build_site.py` reads every `series/<id>.json`'s
  `presentation` block and every `pages/*.json` manifest, and writes one page per
  chart (`/charts/<id>/`), one automatic grid per section (`/<section>/`, sorted by
  `presentation.order`), and one curated page per manifest (`pages/home.json` → `/`).
  It fails the build — naming the offending file — on an unknown section, a missing
  chart-type module, a malformed preset, an unresolved manifest reference, or a
  descriptor id colliding with a built-in type name. Adding a series with an existing
  chart type is therefore mostly a config change; see "Development Patterns" below.
- **Frontend**: native ES modules under `site/js/` — no bundler, no npm, no
  transpiler ("no build step" here means "no JavaScript toolchain"); Plotly.js loaded
  from a CDN `<script>` tag. Each chart *type* is one module in `site/js/charts/`
  exporting `render(el, ctx)` and optional `stats`/`table`/`csv`; `site/js/lib/card.js`'s
  `mount(block, today)` is the only code that plots into a card. No file under
  `site/js` may contain a hex/rgb colour literal — colours come from `ctx.theme`,
  itself read from `site/css/tokens.css`'s CSS custom properties.
- **Custom domain**: CNAME file in deploy sets `joemirza.com`; DNS A records point to
  GitHub Pages IPs (configured in Porkbun)

## Local Iteration Loop

`scripts/dev.sh [port]` (default 8888): runs `python3 scripts/build_site.py
--include-unpublished` (so charts marked `presentation.publish: false` — the S&P 500
P/E — build locally even though they are never deployed)
(generates the multi-page site from `series/*.json`/`pages/*.json` into `site/`, and
copies `data/*.json` → `site/data/`), prints a staleness warning per series, then
serves `site/` with `python3 -m http.server`. No network calls, works with
`FRED_API_KEY` unset — it only reads what's already committed to `data/`, `series/`,
and `pages/`.

The staleness warning matters because local `data/*.json` is known to lag production
(see Architecture above — the workflow never commits fetched data back to `main`).
`dev.sh` surfaces this instead of silently serving old data as if it were current;
it warns, it doesn't block, since UI iteration usually doesn't need fresh data.

**The loop**: edit `site/css`/`site/js`, or a `series/<id>.json` descriptor's
`presentation` block, or a `pages/*.json` manifest, or a fetch script (rerun it
locally with `FRED_API_KEY` set if so) → `scripts/dev.sh` → reload
`http://127.0.0.1:8888/` (or `/economy/`, `/charts/dgs10/`, etc. — use `127.0.0.1`,
not `localhost`, on this machine; `localhost` has repeatedly served a stale cached
response from an unrelated prior project reusing the same port) → check the result
with a Claude in Chrome screenshot → commit and push. The daily workflow handles
fetching, generating and deploying; this loop is only for checking a change works
before it ships.

## Correctness Tests

`tests/` (pytest) checks the data fetchers against independent sources and internal
invariants: `test_data_integrity.py` (dates unique/monotone, no FRED `"."` sentinel
became 0, P/E internal arithmetic, the confirmed/estimated boundary — no network
needed), `test_series_metadata.py` (every `series/*.json` descriptor has its required
fields and valid enums, every input's `source` slug exists in `sources`, `data/*.json`'s
`meta` agrees with its descriptor on the pipeline-owned keys, `as_of.due_by` recomputes
from `last_observation` and the descriptor, the `presentation` schema — allowed
keys/enums, presets grammar, `sections` ⊆ `pages/site.json` — plus the calendar/
period-label fixtures — no network needed), `test_build_site.py` (runs the real
generator against real `series/`/`pages/`/`data/` into a scratch dir — this is what
keeps a broken generator from shipping an empty deploy — plus synthetic-sandbox tests
for every validation failure the generator should catch, the unpublished-series cases
(absent from a default build, built under `--include-unpublished`, a curated block
naming one skipped rather than failing, and the real repo omitting `sp500_pe`), and two source-tree scans of
the committed `site/js/`: no hex/rgb colour literal anywhere, and no `margin`/
`rangeslider`/`height`/`getElementById` outside `lib/plotly-layout.js` and
`lib/card.js`), `test_catalog.py` (every `catalog/sources/*.json` validates through
`scripts/catalog.py`'s own `validate()`; every descriptor `sources[].slug` /
`inputs[].source` / `dataset` reference resolves; descriptor `sources[]` carries only
`{slug, dataset, url, note}`; `meta_from_descriptor()` resolves every descriptor and
the P/E's two entries come out with `via: FRED` and the right terms status; every
committed `data/*.json` names a catalogued slug (old and new `meta.sources` shapes
both accepted); a sandbox negative test per validation rule; the `check`/`report`
CLIs — no network needed), `test_fred_utils.py` (unit tests on the shared FRED helper, mocked,
no network), `test_spreads.py` / `test_yield_curve.py` (sampled dates cross-checked
against FRED's own `T10Y2Y`/`T10Y3M` and a direct `DGS*` pull — need network +
`FRED_API_KEY`), `test_sp500_pe.py` (sp500_pe/sp500_cape/sp500_dividend_yield/
sp500_earnings_yield cross-checked against a fresh pull of Shiller's own columns from
shillerdata.com — needs network, no FRED key), and `test_staleness.py`
(each dataset's `as_of.due_by`, and each input's, against today's US Eastern date;
carries the `staleness` pytest marker so it can run separately from the deploy gate).

Run locally: `pip install -r requirements-test.txt && FRED_API_KEY=xxxxxxxxxxxxxx pytest`.
Tests needing network are marked `network` and skip automatically without a working
connection; run `pytest -m "not network"` to skip them deliberately. Run
`pytest -m "not staleness"` to skip the staleness check specifically (e.g. offline,
where the live-site default below can't be reached).

**Staleness source matters**: `test_staleness.py` checks the *live* site
(`https://joemirza.com/data/*.json`) by default, because local `data/*.json` is known
to lag (see Architecture above) — checking it locally would just re-report that known
gap every time. Set `STALENESS_SOURCE=local` to check the local `data/` copy instead;
the CI workflow does this, running the check right after that day's fetch and before
deploy, when local `data/` is the freshest copy that exists.

## Development Patterns

**Adding a new data series that fits an existing chart type** (`timeseries` or
`curve` — most series will) is file-additive: create files, edit none.
1. `series/<id>.json` — descriptor (title, units, cadence, sources, methodology,
   notes) plus a `presentation` block. `sources[]` entries are references into the
   catalogue — `{slug, dataset?, url?, note?}`, never `name`/`licence` — so the slug
   must exist under `catalog/sources/` (see "Adding a data source" below if it's a
   new rights holder) and `dataset`, when given, must be an id in that file; each
   input may name its `dataset` too. `presentation`: `sections` (which of `economy`/`markets`/
   `rates` it appears on), `order`, `summary`, `chart` (`type` + options — see
   `site/js/charts/timeseries.js`'s payload convention for what `timeseries` needs),
   `stats`, `table`. A descriptor with no `presentation` is a data-only dataset with
   no page (e.g. `usrec`).
2. `scripts/fetch_<id>.py` (or point `series/<id>.json`'s `fetcher` key at an
   existing script, as `dgs10` does at `fetch_treasury.py`).
3. `tests/test_<id>.py` plus a `data/<id>.json` fixture (run the fetcher once
   locally). Parametrize existing cross-cutting tests over `series_meta.ids()`
   rather than adding a new fixture to `conftest.py`.
4. `python3 scripts/build_site.py` — the chart page, its entries on every section
   page it's assigned to, and the nav are all derived from the descriptor. **No
   workflow edit** (`scripts/fetch_all.py` iterates every id in `series/*.json`),
   **no HTML file**, **no nav edit**.

Curating a series onto `/` or a future composite page is a separate, deliberate edit
to `pages/*.json` — never automatic, since that placement is an editorial choice.

**Adding a data source** (a new rights holder, or a new dataset family from an
existing one) is file-additive too: one new `catalog/sources/<slug>.json` (copy
`shiller.json`, the exemplar) or one new entry in an existing file's `datasets[]`,
filled from the source's official pages with `read_from` on every fact block and
`"unknown"` for what couldn't be established, then `python3 scripts/catalog.py check
catalog/sources/<slug>.json` until it prints nothing. The boundary rule decides which
file: a dataset gets its own file only when its terms differ from its host's (S&P
DJI or ICE BofA data on FRED → their own file with `via: fred`) or the publisher
serves it directly; public-domain data reached only through FRED is a `fred.json`
dataset. Full rules and the field table: `catalog/README.md`. Research notes —
including searches that found nothing — go in `catalog/research-log.md`, edited by
the session owner only; a workflow agent puts them in its report for the merge step.

**Keeping a series off the public site**: set `presentation.publish` to `false`. The
chart stays fully configured and still builds, but `build_site.py` derives every page,
section entry, nav link, curated-manifest block and `site/data/<id>.json` copy from the
published set, so the one flag removes it from all five. A manifest that still names it
(`pages/home.json` does) has that block skipped rather than failing the build, so
re-publishing is one flag away. `build_site.py --include-unpublished` — which
`scripts/dev.sh` passes — builds it anyway, which is how `sp500_pe` stays workable
locally. Use this when a source's terms don't permit republishing, not to hide
work-in-progress; an unfinished chart simply has no `presentation` yet.

**Adding a genuinely new chart type** (not expressible as `timeseries`/`curve`
config — needed twice so far, for the P/E's confirmed/estimated split and for the
yield curve's categorical axis + controls) means a new `site/js/charts/<type>.js`
module. See `openspec/specs/chart-components/spec.md` for the render contract
(`render(el, ctx)` plus optional `stats`/`table`/`csv`, all pure except `render`);
`timeseries.js` and `curve.js` are the two worked examples. Rules that apply to every
type: no module-level mutable state (a type can be mounted more than once on one
page), no `document.getElementById`, no hex/rgb colour literal (colours come from
`ctx.theme`), and never set Plotly `margin`/legend position/`rangeslider`/height —
that's `site/js/lib/plotly-layout.js`'s job alone. `tests/test_build_site.py` greps
for violations of the last three rules on every file under `site/js`.

This replaced the pre-2026-09-14 pattern (a new `<button>`+`<div>`+~150 lines of JS
in one file, plus a three-place workflow edit) as part of the `s5-chart-components`
rebuild (S6a→S7c), specifically so two people — or two agents — adding series at the
same time don't conflict on the same file.

## Tech Choices & Rationale

- **Plotly.js** (not matplotlib): Interactive browser charts, supports dropdowns/tabs natively
- **Static site** (not Streamlit): Full control over UI, free hosting, custom domain support,
  no server to maintain
- **GitHub Actions** (not a cron server): Free, reliable, no infrastructure to manage
- **Vanilla JS, native ES modules** (no React/framework, no bundler): a chart *type*
  is one module in `site/js/charts/`; per-series drawing config lives in JSON
  (`series/<id>.json`'s `presentation` block), not hand-written per-chart JS
- **No database**: JSON files are sufficient for this scale; easy to add SQLite or similar later

## Chart Conventions

**Established:**
- Recession shading (USREC) on every time-series chart.
- Monthly-era points labelled as such in the tooltip ("Monthly observation, source: X");
  never upsample monthly to daily.
- Make data gaps (e.g. the yield curve's 2002–2006 tenor gap) visible; don't interpolate
  across them.
- Sequential colour scale for heatmaps; diverging (red/blue) for spreads where zero is meaningful.
- Label the current curve with actual values on the snapshot chart.
- Categorical (evenly spaced) tenor axis on curve snapshots — Bloomberg convention.
- FRED's `"."` is missing, never zero.

**Adopted 2026-09-12:**
- No dual y-axes — **held lightly**, not a hard rule. Dual axes have real uses (two
  series each readable in their own units, easy lead/lag comparison) and no chart
  built so far needs one. Show relationships instead as a scatter plot, a derived
  series, or stacked panels sharing the time axis. Revisit if a future chart
  genuinely wants two axes rather than writing an exception clause preemptively.
- Every chart image carries a short source line and the date of its latest real data
  (not the pipeline run time), drawn inside the Plotly chart itself so PNG exports
  and cropped screenshots keep it (the HTML subtitle does not survive the camera
  button). Full detail goes in the chart's About tab.
- Series that compound over decades plot on a log axis, labelled as log. Doesn't
  apply to yields, ratios, or spreads — only to price levels held over long spans.

**Adopted 2026-09-13 (S4c):**
- Draw a chart only when its container is visible. Plotly sizes a hidden
  (`display:none`) container to a 700px fallback and remembers it on the chart's
  config context. `site/index.html` defers each draw until its tab is first shown and
  calls `Plotly.Plots.resize` on later shows. S5's component contract must say who
  owns this.
- "All", the mode-bar reset and double-click all mean `[first_observation, today]`
  (via `xaxis.autorangeoptions`), never Plotly's padded data extent.
- No range slider on time-series charts. The in-chart source line owns the bottom
  margin band; nothing else is drawn there.

**Adopted 2026-09-17 (S11a):**
- A stitched series (built from more than one source across different eras, like
  `gs10_long`'s Shiller-pre-1953/FRED-post-1953 legs) carries `source` and `frequency`
  on every observation, not just in its descriptor's `inputs[]`. `timeseries.js` shows
  the resolved source's `short_name` on a "Source: X" hover line whenever an
  observation carries one — a no-op on every other chart, since none of them set it.
  This is the concrete implementation of the long-standing "monthly-era points
  labelled as such in the tooltip" convention above, generalized to any stitched
  source, not just a monthly/daily cadence mismatch.

**Adopted 2026-09-13 (S5b):**
- Every chart color is a CSS custom property (`site/css/tokens.css`), never a literal —
  `site/js` (once it exists, S6a/S6b) is expected to hold no hex/rgb literal.
  `getTheme()` reads the tokens at draw time; a `themechange` event redraws every chart
  and table through the existing `renderWhenVisible` mechanism, never a direct
  `Plotly.newPlot` into a hidden tab.
- Light and dark are each their own palette, not a mechanical invert of the other —
  dark's values are an extraction of what the site already used; light's are new,
  independently contrast/CVD-checked (the "dataviz" skill's validator).

Full rationale for the 2026-09-12 and 2026-09-13 additions is in the Session Plan
decisions table at `~/Obsidian/Investing/Finance and Economic Data Website/Session
Plan.md` and in `openspec/changes/archive/*/design.md`.
